# Что отправить агенту, который пишет приложение

Три группы: документы (читать), код-эталон (портировать), фикстуры (проверять).
Плюс отдельно — что отправлять **нельзя** и что словами передать не получится.

---

## 1. Документы — обязательно

| файл | зачем |
|---|---|
| `docs/TZ.md` | собственно ТЗ: сценарии, требования Ф1–Ф15, метрики, лицензии, приватность, открытые вопросы |
| `docs/architecture.md` | итоговый пайплайн: стадии 1–8, цифры каждого шага, формат пака, что проверено и отклонено, что портировать первым |
| `README.md` | структура репозитория, как собираются паки, правила про данные |
| `morphology-analyzers.md` | таблица анализаторов и лицензий (CAMeL, AlKhalil, farahidi, SAMA, Farasa) — нужна, чтобы не выбрать неподходящий по лицензии |
| `assessment-arabic-lookup.md` | исходная оценка задачи: почему клиент-только, какие словари и почему (контекст решений) |

## 2. Код-эталон — портировать на Kotlin

Агент не запускает этот Python, а переносит логику. Порядок отдачи — в §5 architecture.md,
здесь только назначение файлов.

| файл | что внутри |
|---|---|
| `tools/name_class.py` | правила класса «словарное / клитика / имя собственное»: разложение на аффиксы, три условия проверки. Самый важный файл для порта — он определяет 8% метрики |
| `tools/pipeline_full.py` | сбор кандидатов из словарей, поддержка кандидата снаружи, голосование `ksaa → kaikki → wehr`, фильтр (однословные, не коранические, не пассив, не имя собственное) |
| `tools/pipeline_v2.py` | сборка попапа: класс слова → леммы → проба словаря → до трёх статей с дедупликацией по паре «голова + первый смысл» |
| `tools/pipeline_kaikki_ksaa.py` | слияние Kaikki и KSAA, нормализация голов, сопоставление |
| `tools/crossrank.py` | семантика `vote()` / `agreement()` / `decide()` — правила кросс-словарного подтверждения |
| `tools/build_hw_pack.py` | эталон сборки пака: как из исходного sqlite получается пак (схема, нормализация, смыслы) |
| `tools/verify_pack.py` | проверки целостности пака — перенести в экран импорта |
| `tools/hw_inspect.py` | разбор исходного словаря, помогает понять поля |
| `tools/build_kaikki_index.py` | формат индекса Kaikki (6.1 МБ gz из 72 МБ дампа) |
| `tools/eval_live.py` | устройство замера качества; из него делается регрессионный прогон после порта |

Скрипты `tools/eval_arabglossbert.py`, `tools/eval_int8.py`, `tools/eval_sense_llm.py`,
`tools/eval_sense_pair.py`, `tools/sense_prior.py` — это эксперименты, их можно не отправлять;
в них только история решений (в architecture.md она уже изложена).

## 3. Фикстуры — для проверки порта

| файл | что это |
|---|---|
| `data/quality/pf_v2.json` (156 КБ) | **эталонный вывод** по 200 словам: что именно должно оказаться в попапе для каждого слова. Главная проверка порта |
| `data/quality/v2_labels.json` (298 Б) | на какой позиции попапа находится верное значение для каждого из 32 прежних промахов |
| `data/quality/live_labels.json` (42 КБ) | 101 живое предложение с ручной разметкой смысла — для проверки стадии 7 (модель) |
| `data/packs/hanswehr/quality-report.md` (66 КБ) | полный отчёт с методикой и всеми цифрами; содержит текст словарных статей, поэтому только локально |

Эти файлы содержат текст словарных статей KSAA и Hans Wehr — **в публичный репозиторий
их класть нельзя**, даже в `docs/`. Передавай их агенту как локальные файлы и отдельно
скажи: «в git не коммитить, положить в `data/` и не пушить».

## 4. Чего не отправлять

- `data/raw/` — исходные дампы (`hanswehr.sqlite` 16.7 МБ, `kaikki-ar.jsonl.gz` 72 МБ,
  дамп KSAA). Права не позволяют распространять, и они восстанавливаются скриптами.
- Паки `*.sqlite` — тот же смысл.
- Веса модели и каталог `models/` — 500+ МБ и лицензия CC BY-SA (скачивается отдельно).
- Морфологическую базу CAMeL (40 МБ) — GPL-2, качается командой `camel_data -i morphology-db-msa-r13`.

## 5. Что словами, а не файлами

1. **Модель.** `SinaLab/ArabGlossBERT`, CC BY-SA 4.0, 135.2 млн параметров. В приложении:
   ONNX Runtime for Android, int8 ~135 МБ (точность та же, что fp32) или fp16 ~270 МБ.
   Порог разрыва вероятностей 0.3. Скачивается по желанию пользователя, в APK не вшивается.
2. **CAMeL на Android.** Штатно это Python. Варианты: конвертер базы в компактный бинарник
   с Kotlin-поиском по префиксу (предпочтительно) или Chaquopy. Это самый крупный
   инженерный риск порта — оценить отдельно, до начала UI.
3. **Anki.** Интеграция через API AnkiDroid (ContentProvider, разрешение
   `com.ichi2.anki.permission.READ_WRITE_DATABASE`); альтернатива — интент «поделиться»
   с предзаполненным текстом, если API недоступен.
4. **Пункт меню.** `ACTION_PROCESS_TEXT` даёт выделенное слово, но **не** предложение.
   Предложение берётся только через `AccessibilityService`; если его нет — попап работает
   по словарному порядку (это штатный режим, измеренно 88%).
5. **Порядок в попапе неизменяем:** ответ базового пайплайна первым, новые кандидаты ниже.
   Это защита от регрессии, а не вкусовщина.

## 6. Готовое сообщение агенту

> Ты пишешь Android-приложение по приложенному ТЗ (`docs/TZ.md`) и архитектуре
> (`docs/architecture.md`). Ниже — эталонная Python-реализация пайплайна: её надо
> **портировать** на Kotlin, а не запускать.
>
> Ключевые правила, которые нельзя менять при порте:
> 1. Ответ базового пайплайна всегда первая статья попапа; новые кандидаты только ниже.
> 2. Показываем до трёх статей, все смыслы каждой статьи видны.
> 3. Класс «имя собственное» ставится только при трёх одновременных условиях
>    (см. `tools/name_class.py`), иначе теряются настоящие слова вроде `اخرجي`.
> 4. Модель меняет порядок смыслов только при разрыве вероятностей ≥ 0.3.
> 5. Словарные данные в репозиторий не коммитятся: `data/`, `*.sqlite`, `*.jsonl*`,
>    `*.csv`, `*.tsv`, модели — всё в `.gitignore`.
>
> Фикстуры для проверки порта: `pf_v2.json` (ожидаемый попап для 200 слов),
> `live_labels.json` (101 предложение с разметкой). Прогоняй по ним после каждого шага.
> Приёмка: не меньше 90% слов, где нужное значение присутствует в попапе, — на фикстуре
> из 200 слов эталон даёт 93.0%.
