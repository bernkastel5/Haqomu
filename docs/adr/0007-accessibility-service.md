# ADR 0007: сервис доступности — плавающая кнопка и контекст (фаза 8)

Статус: принято 2026-11-14

## Контекст

Ф2 (плавающая кнопка через `AccessibilityService`) и Ф3 (предложение вокруг выделения)
требуют чтения текста экрана. TZ §8 ограничивает: текст используется только для получения
предложения вокруг выделения, не сохраняется и не передаётся; при включении — явное
уведомление. R2: часть приложений (Flutter, WebView, часть ридеров) не отдаёт текст
в дерево доступности — это штатная деградация, а не ошибка.

## Решение

1. **Один сервис, три состояния настройки** (`service/AccessibilityMode`):
   `Off` (по умолчанию) → `Floating` (кнопка у выделения) → `Context` (кнопки нет,
   сервис только запоминает предложение для штатного попапа `ACTION_PROCESS_TEXT`).
   Состояние хранится в `HaqomuPrefs` (`accessibility_mode`) и перечитывается на каждом
   событии: при `Off` сервис не читает ни одного узла и ничего не рисует (сам переключатель
   в системе не трогаем — `disableSelf()` не вызывается, чтобы поведение было предсказуемым
   и обратимым).
2. **Сервис не включается из приложения.** Экран «Доступ к экрану» объясняет, что читается,
   и открывает системный список. При первом включении кнопки показывается диалог-уведомление
   (`floatingNoticeSeen`); текст уведомления повторяет TZ §8 дословно по смыслу.
3. **Минимальная подписка.** В `res/xml/accessibility_service_config.xml`:
   `typeViewTextSelectionChanged|typeWindowStateChanged|typeViewScrolled`,
   `flagDefault`, `canRequestFilterKeyEvents=false`, `canRetrieveWindowContent=true`.
   Никакого `TYPE_WINDOW_CONTENT_CHANGED` и опроса по таймеру; клавиатура не фильтруется.
   Поля с `isPassword` не читаются; при пустом/пробельном тексте сервис молчит.
4. **Окно кнопки — `TYPE_ACCESSIBILITY_OVERLAY`**, а не `TYPE_APPLICATION_OVERLAY`:
   не нужно разрешение `SYSTEM_ALERT_WINDOW` (меньше прав и меньше вопросов при модерации),
   окно живёт ровно столько, сколько подключён сервис. Кружок 42 dp, буква «H», плоская
   заливка deep-green, без иконок, эмоджи, теней и анимаций (`docs/design-guidelines.md`).
   Показ — только при выделении ≥ 2 символов (`FloatingButtonRules.shouldShow`).
5. **Контекст живёт только в памяти процесса** — `service/SelectionHub`: последнее выделение,
   срок 20 с, только для того же слова, сбрасывается при отключении сервиса и при выключении режима.
   Это единственный канал «сервис → попап»; на диск ничего не пишется.
6. **Путь PROCESS_TEXT получает контекст**, если сервис включён и выделение свежее
   (`LookupPopupActivity.readRequest`). Кнопка открывает попап напрямую
   (`LookupPopupActivity.newIntent(word, sentence)`), без повторного чтения экрана.
   `singleTop` + `onNewIntent`: повторное открытие обновляет запрос, окно не плодится.
7. **Контекст виден и используется.** Предложение показывается под словом в попапе
   (3 строки, RTL) и подставляется в поле `Sentence` карточки Anki (TZ §3.3) — и в быстром
   сохранении, и в редакторе. WSD (фаза 9) в этой фазе не включается: порядок смыслов
   остаётся словарным, ответ пайплайна — первой статьёй (D-003, регрессия недопустима).

## Что осознанно не сделано

- **Модель разрешения смыслов** (Ф10) — фаза 9; в попап контекст передаётся, но порядок
  смыслов не меняется.
- **Определение «diff» содержимого по `TYPE_WINDOW_CONTENT_CHANGED`** — не нужно: слово и
  предложение берутся из узла, на котором произошло выделение.
- **Точная геометрия выделенной строки.** `AccessibilityNodeInfo` даёт границы всего узла,
  а не выделенного фрагмента (`getRangeBounds` не API узла). Кнопка ставится у правого края
  узла на высоте его середины и прижимается к границам экрана. Для многострочных текстов
  это приближение; альтернативы (эвристики по строкам через `getBounds` вложенных узлов)
  дают нестабильный результат в разных приложениях.
- **Настройка «показывать кнопку только по долгому нажатию»** — не просили; поведение
  простое и предсказуемое.

## Последствия

- В манифесте появился `service .service.HaqomuAccessibilityService` (`exported=true`,
  `BIND_ACCESSIBILITY_SERVICE`) и `queries` не менялись; новых `uses-permission` нет.
- Приложения, которые не отдают текст, работают через `ACTION_PROCESS_TEXT` как раньше
  (88% по assessment §2): сервис просто не показывает кнопку.
- Строки новых экранов — в RU/EN/AR (210 ключей, наборы совпадают).
- Приёмка на устройстве (см. PROJECT_STATE §5, фаза 8) остаётся: реальное поведение кнопки
  и контекста проверяется только на телефоне.
